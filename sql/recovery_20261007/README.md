# 已执行的正常业务恢复定义

此目录归档 2026-10-07 经验证并已执行的数据库恢复定义，便于今后维护；不是从空库直接执行的安装包。依赖已恢复的业务结构、active 角色判断和私有来源记录。不要重新执行旧 ALL_IN_ONE.sql 覆盖这些修复，也不要未经环境检查重复运行本目录。

- `functions-and-triggers.sql`：21 个前端业务入口、内部辅助函数、12 个触发器；安装阶段撤销新增入口的客户端 EXECUTE，等待权限阶段。恢复旧订单的未知数量保留 NULL，未来新订单使用默认值；缺失历史依据的财务变更会明确拒绝。
- `10-storage-candidate.sql`：两个私有上传桶和对象权限，仅恢复未来上传能力。
- `20-table-write-candidate.sql`：按实际前端通路授予列级写权限及 active 角色 RLS。
- `30-rpc-allowlist-candidate.sql`：最后仅授权明确业务入口，匿名用户与内部辅助函数不开放。
- `40-ui-write-completion.sql`：增量恢复待办状态、便签作者的发布状态、分类启停、本人通知已读和员工手机号写入；待办只记录用户明确选择的员工名字，不触发账户通知。

“candidate”是生成时的原文件名，保留以便与验证散列一一对应；以上文件已通过角色组合测试及线上回滚测试后执行。财务配置、业务记录、Auth 账号、密码哈希、会话、API key 均不在此归档中。

## 验证与限制

本地核心流程 12 组、独立财务审查 11 项、实际 RPC/RLS 组合 80 项、线上回滚资金冒烟 10 项通过。线上测试记录和临时授权全部回滚；单号序列消耗了少量号段，未回调序列。开放写入前的历史业务字段散列与恢复基线相同。

40 增量另经本地实际组合 106 项、线上回滚 13 项验证；VIP 跨升级门槛另有 1 项线上回滚验证通过。员工名字保存后可回读，通知数不增加，且不能以该入口写入 Auth 提及目标。

Storage 已验证数据库策略，未用真实账号执行文件上传端到端测试。PGlite 是单连接环境，并发改进基于行锁/原子增量与确定锁顺序审查，没有把顺序执行宣称为并发压测。旧文件和缺失历史明细无法通过这些定义自动重建。
