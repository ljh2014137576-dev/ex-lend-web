# 订单操作修复（2026-10-08）

原页面允许预约订单直接完成，但恢复后的直接写触发器只允许先开始再完成。单笔详情使用直接 UPDATE，批量使用 RPC，规则与结果解释不一致；批量更新零条时还会按所选条数显示成功。

## 最终行为与入口

| 功能 | 入口和约定 |
|---|---|
| 开始/完成 | 详情页 → `updateOrderStatus` → `set_order_status`；预约可直接完成，必须有员工，状态仅向前推进。核对返回的订单 ID、目标状态和更新数量。 |
| 批量状态 | 列表 → `batch_start_orders` / `batch_complete_orders`；按实际更新 ID/数量及跳过原因显示结果，零条明确显示零条。 |
| 旧页面兼容 | 保留列级 UPDATE(status)，严格触发器采用相同的正向规则，避免仍打开的旧页面继续被拒绝。 |
| 审核台 | 只将已完成、有员工的待审核订单放入候选；批量默认空选，显式勾选。撤销审核成功后刷新为待审核。 |
| 编辑和提成 | 详情弹窗保存真实客户/商品 UUID，不按名字或第一行猜关联；空白提成覆盖为 NULL，表示恢复自动计算。 |
| 删除/异步详情 | 成功后移除共享缓存；请求以订单 ID/代际隔离，避免旧详情响应覆盖当前订单。 |
| 凭证 | 请求结果不明确时保留已上传文件并提示核对，不删除可能已成功挂到订单上的凭证。 |
| 下单确认 | 同步锁阻止同一页面的重复提交；只有明确成功且返回正式订单 ID 才展示成功，小票不以临时 ID 确认。结果不明先核对。 |

共享响应校验与错误说明在 `lib/order-actions.ts`；数据库已执行定义归档在 `sql/recovery_20261007/50-order-status-actions.sql`。订单列表、独立详情页、详情弹窗、审核台和收银台各自保留页面状态，但所有真实写入都以服务器结果为准。

## 保留的业务限制

已恢复旧订单的主记录保留，不继续追补缺失商品明细。开始/完成只改变服务状态，不回放资金事件；缺少历史依据的审核、退款、改价、编辑和删除仍由服务器保护。批量财务审核若选入受保护旧单，整批会拒绝，因此审核台改为明确选择，不自动提交全部历史待审订单。

新订单继续使用原有角色和财务规则。本次没有开放直接修改金额、审核状态、账号权限或私有恢复资料。
